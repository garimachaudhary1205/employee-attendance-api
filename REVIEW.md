# REVIEW.md

Defects I found in the starter `app/main.py`. All of them are fixed in the submitted file. The
helper functions had enough problems that I rewrote them instead of reusing them (rows 1 to 5).

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes`, L36-37 | Grace period compared on floored minutes (`minutes > 10`) instead of seconds. R2 says strictly more than 10:00. | Punch in at 09:40:01 on a 09:30 shift returns 0, but R2's own example says 10. Everything up to 09:40:59 is wrongly "on time". | Compare raw seconds (`delta > 600`), then floor to minutes. |
| 2 | `compute_late_minutes`, L35 | Shift start built with `punch_in.replace(hour, minute)`, which assumes the punch's own calendar day and timezone. | Overnight shift (22:00 to 06:00): a 00:30 punch-in belongs to the shift that started yesterday, but the helper compares against today's 22:00 and returns 0 instead of 150. It also mixes naive datetimes. | Anchor shift start on the record's attendance `date` in IST (`ist_instant(att_date, shift_start)`), always timezone-aware. |
| 3 | `compute_work_hours`, L41 | Python's `round()` is banker's rounding on floats; R4 requires half-up. | 4h07m30s is 4.125 hours. The starter gives 4.12, R4 says 4.13. That also flips `half_day` (R5) in borderline cases. | `Decimal(seconds) / 3600` quantized with `ROUND_HALF_UP`. |
| 4 | `compute_overtime`, L47 | The 30-minute minimum from R3 is missing. | Punch out 5 minutes after shift end returns 5; it must be 0. Sample record 1 (5 minutes over, stored overtime 0) already contradicts the starter. | Floor whole minutes, keep the value only when it is at least 30. |
| 5 | `compute_overtime`, L46 | Shift end is anchored on `date_str` itself, which is the wrong day for overnight shifts (their end falls on the next calendar day). On top of that an aware `end` is subtracted from a naive `punch_out`, which raises `TypeError`, so the request 500s. | An overnight employee punching out at 06:40 next morning gets an overtime figure that is about a day off, or a 500. | Shift end is attendance date plus one day when `shift_end <= shift_start`; every instant is aware UTC (`tz_aware=True` client). |
| 6 | `health`, L72 | Returns `{"status": "ok"}` unconditionally and never talks to MongoDB. | Stop MongoDB and `/health` is still 200; the contract wants 503. The grader polls this before testing. | `client.admin.command("ping")`, 503 on any `PyMongoError`. |
| 7 | module level (nowhere) | No indexes are created at all. Nothing backs `emp_code` or `(emp_code, date)` uniqueness, and every query is a collection scan on the grader's 100k dataset. | `db.employees.getIndexes()` shows only `_id_`; the races in rows 8 and 16 corrupt data instead of returning 409. | `ensure_indexes()` at startup (lifespan), idempotent: unique `emp_code`; unique `(emp_code, date)`; `(date desc, emp_code)`; `(emp_code, punch_in desc)`; `(department, emp_code)`; `(joined_on)`. |
| 8 | `create_employee`, L79-80 | Check-then-insert race on `emp_code`. | Fire several identical creates concurrently: more than one 201 and duplicate employees stored. The contract wants exactly one 201 and the rest 409, enforced by a unique index. | Plain `insert_one`, and `DuplicateKeyError` becomes 409. |
| 9 | `create_employee`, L82 | `datetime.now()` stores a naive server-local time as `created_at`, and the response returns it as an ISO datetime rather than epoch ms. | Run the server in any non-UTC timezone and compare `created_at` with the wall clock; the response field is a string where the contract wants an integer. | Store aware UTC (`now_utc()`), serialize with `dt_to_ms`. |
| 10 | `create_employee` / `EmployeeIn` | No input validation at all: `emp_code` pattern, email, name and department lengths, `HH:MM` format, `joined_on` being a real date, `shift_start != shift_end`. | `POST /employees` with `emp_code: "banana"`, `email: "x"`, `shift_start: "9:30"` or two equal shift times gives 201 instead of 422. | Pydantic field constraints plus explicit checks for equal shifts and impossible dates, all returning 422. |
| 11 | `list_employees`, L93 | `skip = page * page_size`, off by one page. | Page 1 with page_size 20 skips the first 20 employees; the first page can never be seen. | `skip = (page - 1) * page_size`. |
| 12 | `list_employees`, L94 | `total = count_documents({})` ignores the department filter. | Filter by a small department and `total` is still the whole collection, which breaks pagination maths (R10 says total reflects the filters). | `count_documents(q)` with the same filter. |
| 13 | `list_employees`, L95 | No sort (the contract wants `emp_code` ascending) and no bounds on `page` or `page_size` (max 100). | Order can change between calls; `?page_size=100000` returns the whole collection in one response. | `.sort("emp_code")`, and `Query(ge=1)` / `Query(ge=1, le=100)` so out-of-range values are 422. |
| 14 | `punch_in`, L101 | `emp` is never checked for `None`. | Punch in with an unknown `emp_code` and the handler dies with `TypeError` at `emp["shift_start"]`, a 500 where the contract says 404. | `get_employee_or_404`. |
| 15 | `punch_in`, L102-103 | `datetime.fromtimestamp(ms/1000)` produces a naive server-local time, `ts.date()` then takes the server's calendar day rather than the IST day (R1), there is no truncation to whole seconds and no overnight rule at all. | On a UTC server a punch at 01:00 IST on 2026-07-07 (19:30 UTC the day before) lands under `2026-07-06`. Overnight employees get split across two records. | `ms_to_dt` (UTC, `ms // 1000`) and `attendance_date_for()`, which implements R1 including the overnight exception. |
| 16 | `punch_in`, L104-105 | Check-then-insert race: two simultaneous punch-ins both pass the `find_one`, both insert, and with row 7 there is no index to stop the duplicate day. | Ten parallel punch-ins must give exactly one 201 and nine 409s; the starter gives several 201s. | `insert_one` guarded by the unique `(emp_code, date)` index, `DuplicateKeyError` becomes 409. |
| 17 | `punch_in` / `PunchInIn` | `status` is a free string, so ABSENT, LEAVE or garbage are accepted where the contract allows only PRESENT, WFH, ON_DUTY. `punched_at` accepts seconds-looking ints, floats and strings. The response leaks an `"id"` field (records have no id in the contract) and returns `punch_in` as a datetime instead of epoch ms. | `{"status": "LEAVE"}` gives a 201 and creates a leave with a punch time; `punched_at: 1690000000` silently produces 1970-era maths. | A `PresenceStatus` enum, a strict `EpochMs` type (int only, within range) rejecting the rest with 422, and a `record_out()` serializer that emits exactly the contract fields. |
| 18 | `list_attendance`, L144-150 | The whole filtered collection is loaded with `list(...)`, then sorted and paginated in Python. There is also no secondary sort by `emp_code`, no 422 for `date_from > date_to` or malformed dates and status, and `"id"` is leaked again. | On 100k records every call reads everything, which the contract forbids; two records with the same date come back in arbitrary relative order. | `find(q).sort([("date", -1), ("emp_code", 1)]).skip().limit()` with an index hint, `count_documents(q)` for the total, and parameter validation returning 422. |

## Looked at and decided it was not a defect

* `load_dotenv()` without `override=True`. This is correct: a local `.env` is read, but real
  environment variables win, which is what the contract asks for.
* `status_code=201` on `POST /employees` and `POST /attendance/punch-in` matches the contract.
* `doc.pop("_id", None)` after `insert_one` works, because `insert_one` mutates the dict it is
  given. I kept the idea but moved it into the serializers.
* Storing `date` as a plain `"YYYY-MM-DD"` string is correct per DATA_MODEL.md; a calendar date
  is deliberately not an instant.
* The `MONGO_URI` and `MONGO_DB` fallback defaults are fine as local conveniences; nothing is
  hard-coded once the environment provides values.
